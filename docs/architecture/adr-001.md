## ADR-001a: Authentication Provider {#auth}

**Status**: Accepted

### Context

Coin needs authentication that supports social login (X / Farcaster / email), embedded Solana wallets (users never see seed phrases), and MPC or enclave-based key management. The PRD specifies Privy. The Architecture Blueprint specifies Clerk.

### Options Considered

**Privy (Selected)**
- Native Solana embedded wallets
- MPC + enclave-based key management
- X (Twitter) + Farcaster + email login
- Social recovery (no seed phrases)
- Built for crypto-native apps
- Wallet auto-created on signup
- Free tier supports MVP

**Clerk (Blueprint)**
- SOC 2 Type 2 certified
- Bot protection + breach detection
- 10K MAU free tier
- No native Solana wallet support
- No embedded crypto wallets
- Would require separate wallet provider
- Built for traditional web apps

### Decision

**Use Privy for authentication and embedded wallets.** Coin is a crypto-native product where every user needs a Solana wallet. Privy provides auth + wallet as a single integration. Using Clerk would require bolting on a separate wallet provider, adding complexity with no benefit.

### Consequences

- Single SDK handles both auth and wallet provisioning
- Users sign in with one tap — no MetaMask, no seed phrases
- Privy handles key recovery via social login
- Trade-off: Privy lacks Clerk's bot protection and breach detection (mitigated by Cloudflare WAF if needed later)

:::caution Open Decision (Phase 2a)
Final wallet provider choice (Privy embedded vs Phantom embedded vs Turnkey vs Crossmint) will be confirmed during a Phase 2a technical spike. Privy is the default unless the spike reveals a blocker.
:::

## ADR-001b: Backend Architecture {#backend}

**Status**: Accepted — Revised Feb 23

### Context

Both the PRD and the Architecture Blueprint agree on Convex as the primary backend. The blueprint additionally proposes 6 Hono-based microservices deployed on Fly.io. Team feedback (dEXploarer) argues that relying solely on Convex Cloud is too limiting — a Hono server layer alongside Convex provides more control over compute, webhooks, and long-lived connections.

### Decision

**Convex as the primary data layer + a thin Hono server for compute that doesn't fit serverless.** Not 6 independent microservices — one Hono process alongside Convex, handling the workloads listed below.

### Responsibility Split

**Convex (Data Layer — Primary)**
- Offer CRUD (create, accept, cancel)
- Real-time subscriptions (marketplace feed)
- User data, agent config, reputation
- Scheduling (cron jobs, cleanup)
- File storage (KYC docs, avatars)
- ACID transactions for state changes
- Optimistic updates for UI

**Hono (Compute Layer — Companion)**
- Webhook receivers (Privy, Solana tx confirmations)
- Agent health checks & admin API
- WebSocket fan-out for price feeds
- Long-running compute (batch operations)
- External API orchestration
- Rate limiting & request validation
- Any future PCI-isolated processing

### Blueprint Microservices — MVP Mapping

| Blueprint Microservice | Coin Equivalent | MVP Decision |
|------------------------|-----------------|--------------|
| Trading Engine (Hono) | On-chain escrow + Convex offer management | Convex + escrow program |
| Payment Processor | N/A — all settlement on-chain via USDC | Not applicable |
| Compliance Engine | US geo-blocking via Vercel Edge Middleware | Middleware only |
| Notification Service | Convex real-time subscriptions | Built into Convex |
| Market Data Service | Jupiter WebSocket price feeds | Hono layer in coin-agents |
| Analytics Service | Not in MVP scope | Deferred to V2 |

:::tip Why this split works
Convex handles all data operations, real-time sync, and ACID guarantees. Hono handles everything that needs raw HTTP control, long-lived connections, or sits outside Convex's serverless model. The Hono process runs on Railway alongside the agent workers — no additional infrastructure.
:::

### When to Split into Separate Services

Introduce dedicated microservices in V2+ if: (a) fiat on-ramp requires PCI-isolated processing, (b) Python-based ML workload (fraud detection) needs its own runtime, or (c) independent scaling is needed for a specific compute workload.

## ADR-001c: Repository Structure {#repos}

**Status**: Accepted

### Context

The Architecture Blueprint proposes a Turborepo + pnpm monorepo. The team has already created 5 separate repositories under the `coin-agent-exchange` GitHub organization.

### Decision

**Keep the multi-repo structure for MVP and V1. Evaluate monorepo migration for V2.**

### Current Repository Layout

| Repository | Technology | Purpose |
|------------|-----------|---------|
| `coin-web` | Next.js + Tailwind | Consumer web application |
| `coin-convex` | Convex (TypeScript) | Backend: schema, queries, mutations, actions |
| `coin-escrow` | Anchor / Rust | Solana escrow program (on-chain settlement) |
| `coin-agents` | TypeScript / Node.js | Agent runtime workers (market makers) |
| `coin-prd` | HTML / PDF | Product docs (PRD, roadmap, ADRs) |
| `coin-docs` | Docusaurus | Documentation site (this site) |

### Type Sharing Strategy

To share TypeScript types between `coin-web`, `coin-convex`, and `coin-agents` without a monorepo, publish a `@coin/types` npm package (private, on GitHub Packages) or use Git submodules. Decision on exact mechanism deferred to Sprint 1.

## ADR-001d: Cloud Platform & Hosting {#hosting}

**Status**: Accepted — Revised Feb 23

### Context

The PRD/roadmap specifies free-tier infrastructure for MVP (&lt;$50/mo) scaling to ~$4K/mo post-funding. Team feedback (dEXploarer) raised an important point: **self-hosting Convex on Railway** provides data sovereignty over user wallet data and trade history. Convex is fully open-source and has a one-click Railway deploy template.

### Decision

**MVP: Convex Cloud (zero ops, ship fast). V1: Migrate to self-hosted Convex on Railway (data sovereignty).** Vercel for web, Railway for agents + Hono + self-hosted Convex, Helius for RPC.

### Hosting Map

| Component | MVP (Free Tier) | V1 Post-Funding |
|-----------|----------------|-----------------|
| **Web App** (coin-web) | Vercel Hobby ($0) | Vercel Pro ($20/mo) |
| **Backend** (coin-convex) | Convex Cloud Starter ($0) | Self-hosted Convex on Railway + Postgres (~$20–40/mo) |
| **Agents + Hono** (coin-agents) | Railway Hobby ($5/mo) | Railway Pro ($20/mo) |
| **Escrow** (coin-escrow) | Solana Devnet (free) | Solana Mainnet |
| **RPC** | Helius Free (100K/day) | Helius Growth |
| **CDN / WAF** | None (Vercel handles CDN) | Cloudflare (if needed) |
| **Monitoring** | Vercel Analytics (free) | Sentry + Vercel Analytics |
| **CI/CD** | GitHub Actions (free) | GitHub Actions |

### Monthly Cost Projection

| Phase | Monthly Cost | Notes |
|-------|-------------|-------|
| MVP (Weeks 1–4) | **&lt;$50/mo** | All free tiers + $50–200 one-time seed |
| V1 (Weeks 5–16) | **~$4,000/mo** | Vercel Pro, self-hosted Convex + Postgres, Helius Growth, Railway |
| V2+ | **$8–15K/mo** | Additional services as needed |

### Self-Hosted Convex Migration Plan

:::warning Amendment (Feb 23)
Based on team feedback from dEXploarer: self-hosting Convex provides data sovereignty over user wallet data, trade history, and financial activity. For a crypto product, controlling your own data infrastructure is a meaningful privacy and security advantage.
:::

Convex is fully open-source (FSL Apache 2.0) and supports self-hosting via Docker with SQLite or Postgres.

| | Convex Cloud (MVP) | Self-Hosted on Railway (V1) |
|---|---|---|
| **Setup** | Zero config | Docker + Postgres (one-click template) |
| **Scaling** | Automatic | Manual (scale vertically on Railway) |
| **Data Privacy** | Convex Cloud servers | Your infrastructure — full sovereignty |
| **Cost** | $0 → $25/mo | ~$20–40/mo |
| **Backups** | Managed | Team-configured (S3 backup template) |
| **Dashboard** | dashboard.convex.dev | Self-hosted (open-source) |

**Migration Path:**
1. **MVP (Weeks 1–4):** Convex Cloud free tier. Zero ops, ship fast.
2. **V1 Phase 1 (Week 5):** Deploy self-hosted Convex on Railway + Postgres. Migrate from Cloud.
3. **V1 Phase 2+:** Agents, Hono, and Convex all on Railway. Single platform, full control.
4. **Migration is low-risk:** Same API, same client libraries. Only the backend URL changes.

## ADR-001e: QA & Production Environments {#environments}

**Status**: Accepted

### Decision

**Two-environment strategy** leveraging Solana's devnet/mainnet split and Vercel's preview deployments.

| Layer | Development / QA | Production |
|-------|-----------------|------------|
| **Solana** | Devnet | Mainnet |
| **Web App** | Vercel Preview (auto per PR) | Vercel Production (`main` branch) |
| **Convex** | Dev project | Production project |
| **Agents** | Local / Railway Dev | Railway Production |
| **RPC** | Helius Devnet endpoint | Helius Mainnet endpoint |

### Deployment Flow

1. Developer pushes feature branch → Vercel auto-generates Preview URL
2. PR reviewed by at least one team member + CI checks pass
3. Merge to `main` → Vercel deploys to Production + Railway deploys agents
4. Escrow program upgrades: tested on Devnet, deployed to Mainnet after full team sign-off

:::caution V1 Upgrade
Add formal staging environment post-funding. Blueprint's canary deployment pattern (5% → 25% → 50% → 100%) adopted in V2 when there's real user traffic to split.
:::

## ADR-001f: Vector Database {#vectordb}

**Status**: Deferred

### Decision

**Neither Pinecone nor Qdrant is needed for MVP or V1.**

Coin's MVP and V1 do not include features requiring vector embeddings:
- No AI-powered search — token pairs are a fixed list of 14
- No recommendation engine — marketplace shows all offers
- No robo-advisory — users and agents trade directly
- No fraud detection ML — escrow + spending limits handle safety

### If/When We Need One

| Option | Type | Pros | Cons |
|--------|------|------|------|
| **Convex Vector Search** | Built-in | Zero additional infrastructure | Less mature |
| **Pinecone** | Managed SaaS | Zero ops, fast, free tier | Vendor lock-in |
| **Qdrant** | Self-hosted | Open source, cheaper at scale | Requires ops |

:::tip Recommendation for V2+
Try Convex's built-in vector search first. If the use case outgrows it, migrate to Pinecone for managed simplicity.
:::

## ADR-001g: State Management & Patterns {#patterns}

**Status**: Accepted

### Decision

Adopt the following patterns from the Architecture Blueprint:

| Pattern | Adoption |
|---------|----------|
| **Client State** | Zustand for UI state, Convex for server state |
| **Validation** | Zod schemas on every boundary |
| **Forms** | React Hook Form + Zod |
| **Styling** | Tailwind CSS 4 + shadcn/ui |
| **Convex Organization** | queries.ts / mutations.ts / actions.ts per domain |
| **Feature Modules** | Vertical slices (components, hooks, actions, stores) |
| **Component Hierarchy** | Primitives → Composites → Features → Pages |
| **Error Boundaries** | App → Layout → Feature → Component |
| **Optimistic Updates** | Convex built-in support |

**Not adopted:** LaunchDarkly feature flags (use env vars), ClickHouse (no analytics workload), Redis/Upstash (Convex handles caching), Pulumi IaC (3 services don't need it), Infisical secrets (use platform env vars).
